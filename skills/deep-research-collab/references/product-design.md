# 产品设计（product-design）
> 本文件防止的失败模式：技能做成"长时间黑箱然后吐一份报告"，用户在过程中看不到中间产物、无法纠偏；以及把本轮的示例行业当成通用规则，导致技能只能服务一个案例。

## 1. 3 分钟可见结果

**3 分钟可见结果：从用户发出调研请求算起，3 分钟内必须先给出一页 `research brief`（Markdown，屏幕上直接可读），再开始任何长耗时的深度检索。**

这一页 brief 的字段（固定，缺项即不合格）：

| 字段 | 内容 | 作用 |
| --- | --- | --- |
| 研究主题 | 用户的 `原始意图` 逐字引用 + 一句话意图转述 | 让用户立刻确认"你理解的是不是我要的" |
| 边界 | 做什么 / 不做什么；本轮覆盖的 `research_domain` 范围；时间范围 | 提前砍掉跑偏方向 |
| 指标体系 | 报告要回答的核心问题清单（3–7 条）+ 每条需要的证据类型 | 把"调研"变成可验收的问题集 |
| 证据路线 | 三级搜索协同的分工与预计检索量、成本 | 让用户知道钱和时间花在哪 |
| 交付物形态 | `deliverable_target`：文档版报告（Markdown）+ 单文件离线 HTML 交互式报告 | 让用户对最终形态有预期 |

时间与预算口径：

- 3 分钟内允许的动作：读用户材料、跑 `Local capability inventory`、写 brief。**不允许**在 brief 之前启动大规模检索。
- 若 3 分钟内无法给出 brief（材料严重不足），必须立刻给"缺什么材料"清单并停下，而不是默默开始猜。

## 2. 体验流程设计

用户在本技能中的三个关键介入点（其余步骤自动推进）：

| 介入点 | 时点 | 用户给什么 | 用户看到什么 | 不确认的后果 |
| --- | --- | --- | --- | --- |
| P1 输入 | 起点 | `原始意图`、`research_domain`（可为空，由本技能推断）、`audience`、`deliverable_target`、已有材料（可选） | 无 | 意图转述错误，后续全部返工 |
| P2 确认 brief | ≤ 3 分钟 | 确认 / 修正 主题、边界、指标体系 | 一页 `research brief`（第 1 节字段） | 指标体系错，报告答非所问 |
| P3 确认报告结构 | 阶段 2 结束、阶段 3 开始时 | 确认 / 调整章节树与重点 | 认知地图 v1.0 摘要 + 报告章节树（章节 = 论证目标）+ 图表清单 | 结构与 `stakeholder_view` 不匹配，输出后才发现要重排 |
| P4 交付前确认（可选，建议保留） | 阶段 4 结束 | 确认取舍口径（哪些结论进正文、哪些进"待补证"） | 文档版报告 + HTML 报告，以及未通过门禁项清单 | 取舍口径与读者期待不符 |

中间产物必须**可看见**（写入文件并在会话中给出摘要），至少包括：`00-research-brief.md`、`01-candidate-sources.md`、`02-evidence-v1.0.md`、`03-cognition-map-v1.0.md`、`02-evidence-v2.0.md`、`03-cognition-map-v2.0.md`。

长耗时检索期间的表现要求：每完成一个检索层级给一行进度（已用检索次数 / 剩余预算 / 已获取 EV 数 / 已识别缺口数）。禁止长时间无输出。

## 3. 例子不是元规则

**例子不是元规则：reference 中的任何示例行业、公司名、岗位名、受众描述、一次性验收短语，都只用于说明，不得进入判据、门禁、默认值与路由规则。**

具体约束：

1. 所有示例必须显式标注，格式：`> —— 以下为示例，不进入规则`。
2. 变量优先：`research_domain`（行业/领域）、`audience`（受众）、`target roles`（报告接收角色）、`stakeholder_view`（利益相关方视角）、`deliverable_target`（交付目标）一律写变量名。
3. 替换自检（写完必做）：把示例里的行业名、公司名、岗位名全部替换为 `XXX`，规则句必须仍然成立。若替换后句子读不通、或门禁结果改变 → 说明规则被案例绑定，必须重写。
4. 反向约束：若某条规则只对特定行业成立（例如某行业的合规要求），它必须写成本轮的 `证据路线` 或 `不可得路径` 内容，而不是写成通用 Hard Stop。
5. 一次性验收短语（如"这次汇报用""本周内交付"）只允许出现在 `原始意图` 的逐字引用里，不得成为任何判据。

## 4. 当前边界（不做的事）

| 不做的动作 | 判定 | 被要求时的回应 |
| --- | --- | --- |
| 不伪造来源 | 任何编造链接、标题、原文片段、发布时间的行为 | 拒绝；给出"待补证"记录 |
| 不替代人工判断 | 不替 `stakeholder` 做风险取舍、不代替决策、不承诺行动建议的后果 | 给证据与选项，标注不确定度，让 `stakeholder` 决定 |
| 不承诺无证据结论 | 无证据 ⇒ 不写确定性结论；来源 < 2 ⇒ 不标核心结论 | 转 `research-needed` 或降级为"待验证判断" |
| 不做发布 / 付费动作 | 不发布内容、不投放、不下单、不代付费、不执行任何外部写操作 | 明确说明停在"交付文件"，发布由用户执行 |
| 不做合约外检索 | 不绕过付费墙、不抓取需登录内容 | 记入 `不可得路径` 并给替代口径 |

边界不是拒绝服务，而是**换成可交付的替代动作**：拒绝伪造就提供"待补证"清单；拒绝发布就交付可自行发布的文件。

## 5. 先做意图领域研究

**先做意图领域研究：阶段 0 之后、任何检索与任何表面设计之前，先产出 `Domain Research Brief`（见 `intent-domain-research.md`）。**

在流程中的位置：

```
P1 用户输入
  → Local capability inventory（实测）
  → Domain Research Brief   ← 必须先做
  → 3 分钟可见的 research brief（P2 确认）
  → 阶段1 广度候选检索
  → …… → HTML 交付
```

禁止的顺序（出现即回退）：

- 先写报告大纲，再找证据；
- 先定 HTML 模板/图表样式，再做领域研究；
- 先写结论，再补来源。

## 6. Local Capability

产品设计只能使用**实测可用**的能力。设计表面之前先跑一遍 `Local capability inventory`（字段：`capability` / `name` / `version` / `invoke` / `surface_use` / `limits` / `cost` / `usable` / `fallback`）。

实测参考（每次运行前建议复核，环境可能变化）：

| 能力 | 实测结果 | 对产品设计的影响 |
| --- | --- | --- |
| `tvly`（Tavily CLI，可执行文件名是 `tvly`，**不是** `tavily`） | 本机可用，`tavily-cli 0.1.8` | 一级广度发现（全球域）可用；受 Tavily 计划额度上限约束 |
| 秘塔 MCP 六工具 | 可用：`metaso_web_search` / `metaso_web_reader` / `metaso_chat` / `metaso_topic_list` / `metaso_topic_search` / `metaso_topic_file_content`（完整前缀 `mcp__metaso__`） | 一级中文域广度、二级中文/公众号深读、三级缺口补充可用；每次检索约 3 积分，必须计入成本边界 |
| Chrome | 本机存在（`C:\Program Files\Google\Chrome\Application\chrome.exe`） | HTML→PDF 与截图归档可用 |
| 文档版报告 | Markdown | 交付物①形态确定 |
| `python` | 当前不在 PATH（探测结果 NOT FOUND） | `python scripts/check_meta_skill_package.py .`、`python scripts/check_closed_loop.py .` 可能需先确认解释器路径；不得因命令报 not found 就宣称校验通过 |

## 7. Multimodal

HTML 交互式报告是本技能唯一的**多模态表面**；文档版报告保持纯文本可 diff、可版本对比。两者内容必须 100% 一致。

| 模态元素 | 用途 | 硬约束 |
| --- | --- | --- |
| SVG 图表（柱状 / 占比） | 数据类结论 | 只能画有来源的数据；图中标注来源 EV |
| 思维导图 | 体系与概念关系 | 分支 ≤ 3 层；叶子尽量挂 EV |
| 流程图 | 阶段 / 决策链 / 转化路径 | 节点附 EV 标签 |
| 证据链路图 | 结论 → 证据 ID → 来源的连线 | 每条结论至少 1 条边 |
| 时间线 | 事件与版本演进 | 每点带日期与来源 |
| 正反对置面板 | 争议观点 | 左右各挂证据 ID，缺一侧禁止渲染 |
| 交互控件（筛选 / 检索） | 按类型与可信度筛选、关键词检索 | 离线可用，无外部依赖 |

多模态红线：HTML 中出现无证据 ID 的结论 → 不合格；图表无来源 → 不合格；中文文本烘焙进 SVG 且本机缺字体 → 改为 HTML 文本渲染。

## 8. Loop Closure Board

每轮结束（阶段 5 归档时）必须填这张板，作为下一轮的输入。

| 字段 | 必须写什么 |
| --- | --- |
| `本轮结论` | 本轮得到的结论清单（含证据 ID 覆盖度：每条结论绑定几个 EV） |
| `证据缺口` | 仍未解决的 `research-needed` 项、`不可得路径` 清单，以及下轮可用什么替代口径 |
| `写回决策` | `writeback`（写回哪个文件、写了什么判据）或 `none-with-reason`（一句话理由 + 规则已覆盖的证据） |
| `下一轮复用 key` | 可复用的检索式、已验证的来源渠道、已确认的工具真名与版本、已定型的表面选择（如"争议型结论 → 正反对置面板"） |

判定规则：

- `下一轮复用 key` 必须写成可直接复制使用的形式（检索式给原文；来源给链接；工具给真名+版本）。
- 若某条 `证据缺口` 连续两轮未解决，必须在板上标注 `escalate`，并写清需要用户提供什么材料。
- `写回决策` 为 `writeback` 时，必须在同一轮内完成写回动作，不留待下轮。
