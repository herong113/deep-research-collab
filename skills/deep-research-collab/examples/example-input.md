# 示例输入

> 本文件防止的失败模式：技能被当成"随便搜搜"的提示词，导致缺少边界、缺交付物形态、无法验收。

## 一次真实的模糊委托（原始输入）

```text
帮我研究一下 AI 编程助手这个赛道，我想给团队做技术选型前的判断，
每个结论都要有来源，最后给我一份能演示的报告。
```

## 用户材料

| 项 | 内容 |
|---|---|
| 已有材料 | 无正式文档；只有两次内部会议的口头印象 |
| 可访问资源 | 公网检索工具（Tavily / 秘塔 / 微信公众号定向检索） |
| 时间预算 | 当轮内完成初版；深度补搜可在下一轮追加 |
| 约束 | 不接受无来源的结论；不接受把某个具体厂商的名字写死成规则 |

## 需要在本阶段锁定的变量

| 变量 | 本次取值 | 为什么必须锁定 |
|---|---|---|
| `research_domain` | AI 编程助手（国内为主，兼顾海外） | 决定检索语言、来源类型与关键词 |
| `audience` | 团队技术选型会 | 决定深度与"是否值得投入"的结论粒度 |
| `deliverable_target` | 归档 + 演示（默认双交付） | 决定是否需要 HTML 交互式报告 |
| `stakeholder_view` | 工程负责人视角 | 决定优先核对哪些指标 |
| `time_window` | 近 18 个月 | 决定证据时效红线 |
| `excluded_scope` | 不做代码质量实测、不做报价谈判 | 防止任务膨胀 |

## 反例（不应当这样开始）

- ❌ 直接开始网页检索，不写研究简报 → 后面无法判断"证据够不够"。
- ❌ 先决定用思维导图 + 四张图表，再去找能填满图表的数据 → 属于"先定表面后找证据"。
- ❌ 把"AI 编程助手"替换成"任何行业"后规则不成立 → 说明把案例变量写成了规则。
